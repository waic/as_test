# テスト手順と期待される結果の書式

この文書は、テストケース Markdown における「テスト手順」と「期待される結果」の書式を定める案である。書き方を 1 つに絞るのではなく、テストケースの性質に応じて複数の書き方を認める「複数容認案」とする。

- 背景: [既存のテストの手順と期待される結果を対にする (Issue #174)](https://github.com/waic/as_test/issues/174)
- 検討の場: [PR #321](https://github.com/waic/as_test/pull/321)
- 状態: WIP（WG2 で合議して確定する）

## 目的

テスト手順と期待される結果を対にして書くことで、次のことを可能にする。

- テスト実施者が「この手順を実施したときに何を確認するのか」を一目で確認できる
- テスト結果の入力（AS情報作成のエクセル等）における「期待される結果 n. に対する操作内容」「期待される結果 n. を満たしているか ?」といった列との対応が明確になる
- テスト手順と期待される結果を分けて読み込むツール（AS-Test-tool 等）による入力 UI の改善

## 結論（提案する書き方）

閲覧環境ごとに「テスト手順」と「期待される結果」を対として書く。対の見出しは、次の 2 通りを認める。

- **対見出し（統合形）**: `# テスト手順と期待される結果 (視覚閲覧環境)` または `# テスト手順と期待される結果 (音声閲覧環境)` の見出しの下に、`## テスト手順` と `## 期待される結果` を書く。新しいテストケースではこちらを推奨する
- **分離形**: 手順が 1 つのテストケースでは、従来どおり `# テスト手順 (視覚閲覧環境)` と `# 期待される結果 (視覚閲覧環境)` の 2 つの見出しに分けて書いてもよい

対の中身は、テストケースの性質に応じてさらに次の書き方を認める。

- **複合**: 1 つの手順に対して複数の確認事項がある場合（「次の 1.〜n. をすべて満たしている」等）は、それらをまとめて 1 つの「期待される結果」に書いてよい
- **並列**: テスト手順が複数あるときは、分離形とせず、対見出しの下に `## テスト手順 1` と `## 期待される結果 1`、`## テスト手順 2` と `## 期待される結果 2` のように、番号を付けて対にする

テスト不要の環境は、対応する見出しを置いたうえで「テスト不要」「なし」と書く。

### 単一・複合の例（対見出し・手順が 1 つ）

    # テスト手順と期待される結果 (音声閲覧環境)

    ## テスト手順

    見出しを読み上げ、内容を確認

    ## 期待される結果

    次の 1. 〜 3. をすべて満たしている

    1. 見出し要素に差し掛かると、それが見出しであることが通知される
    2. 見出しレベルを知るための何らかの手段が提供されている
    3. 見出しの内容と見出しレベルが合致している

### 分離形の例（既存の多くのテストケースはこの形）

    # テスト手順 (音声閲覧環境)

    リンクを読み上げ、内容を確認

    # 期待される結果 (音声閲覧環境)

    アイコン画像の代替テキストは何も読み上げられず、リンクテキスト “…” のみが読み上げられる

### 並列の例（手順が複数）

    # テスト手順と期待される結果 (音声閲覧環境)

    ## テスト手順 1

    role="slider" が指定されたスライダーにフォーカスを移動する。

    ## 期待される結果 1

    スライダーにフォーカスが移動でき、スライダーの名前が「音量」、スライダーであること、及び現在値「30」が認識できる。

    ## テスト手順 2

    矢印キーを使用してスライダーの値を変更する。

    ## 期待される結果 2

    矢印キーでスライダーの値を変更でき、変更後の現在値が認識できる。

### テスト不要の例

    # テスト手順と期待される結果 (視覚閲覧環境)

    ## テスト手順

    テスト不要

    ## 期待される結果

    なし

## 規則

1. 閲覧環境ごとに「テスト手順」と「期待される結果」を対として書く。見出しは対見出し（`# テスト手順と期待される結果 (…)`）を推奨するが、手順が 1 つのテストケースでは分離形（`# テスト手順 (…)` と `# 期待される結果 (…)`）でもよい。
2. 対見出しの下では、テスト手順が 1 つのときは `## テスト手順` と `## 期待される結果` のように番号を付けない
3. テスト手順が複数のときは、対見出し（分離形としない）の下に `## テスト手順 n` と `## 期待される結果 n` を交互に書き、n は 1 から始まる連続した番号として、テスト手順 n と期待される結果 n を 1 対 1 で対応させる
4. 1 つのテスト手順から複数の確認事項が生じる場合は、その複数の事項をまとめて 1 つの「期待される結果」としてよい。この場合、判定はすべての事項を満たしているかどうか（AND 判定）となる
5. 逆に、1 つのテスト手順に対応しない複数の番号付き項目を「期待される結果」として列挙する書き方は避ける（手順が複数あるなら規則 3 に従い、対にして書く）
6. テスト不要の環境は、対応する見出しを置いたうえで「テスト不要」「なし」と書く
7. テスト実施時の注意点は、閲覧環境のセクションの後（`# テスト実施時の注意点 (…)` 見出しの下）に書く。特定の「期待される結果 n」に関する注意点を書くときは、その注記の中で「期待される結果 n」と番号を明示して参照する

## この書き方にした根拠（実データ）

全テストファイルの「テスト手順」＋「期待される結果」セクション 268 件を構造で分類すると、次のとおりである。

| 分類 | 内容 | 件数 |
| --- | --- | --- |
| 単一 | 手順 1 つ → 結果 1 つ | 127 |
| 複合 | 手順 1 つ → 複数の確認事項（「すべて満たしている」等） | 50 |
| 並列 | 手順が複数 → 結果も複数（15 件のうち 14 件が既に対形式） | 15 |
| テスト不要・なし | 手順が「テスト不要」、結果が「なし」等 | 69 |
| 不一致 | 手順の項目数と結果の項目数が合わない | 5 |
| 結果セクションの欠落 | 見出しの取り違え等 | 2 |

（合計 268 セクション。単一 127 には、環境名のない H1 結果見出しを持つものを含む）

分かったことは次の 3 点である。

第 1 に、**手順そのものは 1 つで、確認事項だけが複数**という「複合」が 50 件ある。この型は、手順を複数に分割すると「確認作業の列挙」になり、実施者の実際の操作（読み上げて確認する 1 回など）と乖離する。0003-01 のように「次の順序でフォーカスが移動する」の箇条書きが 18 項目にわたる例もあり、分割は現実的でない。したがって複合はそのまま許容するのが妥当である。同様に、手順 1 つ・結果 1 つの単一が 127 件と最も多く、これに見出しの番号を足しても情報量は増えない。

第 2 に、**並列（手順が真に複数）の 15 件のうち 14 件は、既に対形式で書かれている**。取り残されているのは 0057-02 の 1 件である。「手順が複数なら対にする」と規定するだけで、既存の過半と整合する。

第 3 に、**対形式は Issue #174 で初めて導入されたものではなく、4 年間にわたって繰り返し選ばれてきた書き方**である。

| 時期 | テスト | コミット |

このうち 0057-01（対形式）と 0057-02（旧形式）は同じシリーズであり、0057-02 は「新しい記法を作った」のではなく「同シリーズの先行事例が使っていた対形式を踏襲しなかった」ものである。分離形を許容する場合も、**手順が複数のときは対見出しに統一する**（規則 3）ことで、この種の不揃いは解消できる。

## 修正が必要な箇所

分離形を許容する場合でも、次の修正は必要である。このブランチでは、下記を実際に実施した（実施内容の検証も済み）。方針の妥当性を、修正そのものによって確認できる形にしている。

### 検証

- 修正済みの 3 ファイル（0057-02・0034-01・0119-01）では、番号対応の不一致と「手順 n と結果 n の対応が取れない」状態が解消されている
- 各ファイルの行末コード（CRLF/LF）を保持し、diff が修正箇所のみになっている（全行書き換えのノイズなし）
- markdownlint 201 ファイル・0 エラー

## この PR で扱う範囲

この PR は「書式の案と、その適用例」である。方針の妥当性を、修正そのものによって確認する目的で、最低限のテストファイル修正（上表の 3 ファイル + 0012-01）を含める。

- 案の妥当性に加え、修正済みテストファイル（0057-02・0034-01・0119-01）の中身が期待どおりかを確認してほしい
- 不一致の残り（0052-01／0054-01／0093-01／0006-03）は、修正の方向を WG2 で確認してから行うのがよい
- 分離形（旧形式）を許容するため、既存テストケースの見出し置き換えは行わない。既存の大半のファイルは無変更である

## 今後の検討事項

1. 既存テストケースをこの書式に統一する時期と進め方（機械的に直せるものと、内容を確認して直すものがある）
2. 番号を付けた対（並列）で、他テストの結果から「期待される結果 2」のように番号参照する運用がある場合の扱い
3. AS-Test-tool や結果入力ツールが、番号（`n`）を必要とするか、H2 見出しの並び順だけで足りるか
4. この書式を自動検証する仕組み（CI）を導入するかどうか
